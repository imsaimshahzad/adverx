# AdverX Naming Conventions

This document defines naming rules for new and modified AdverX code. It deliberately does not rename existing files, database objects, RPCs, or financial functions automatically: those names may be referenced by imports, Supabase policies, deployed SQL functions, API routes, or historical migrations.

## Source code

- React components and component files: `PascalCase` (for example, `AdminEmailComposer.tsx`, `TransactionRow.tsx`).
- React hooks: files and exported hook names start with `use`; preserve the repository's established hook style where touching existing files (current example is `use-mobile.tsx` exporting `useIsMobile()`).
- Functions and local variables: `camelCase` (for example, `fetchUsers`, `isVerified`, `handleApproveWithdrawal`).
- Boolean names should communicate a yes/no state with prefixes such as `is`, `has`, `can`, or `should`.
- Constants: `UPPER_SNAKE_CASE` for module-level values that are true constants (for example, `MAX_DAILY_REWARDS`); do not convert ordinary variables to constants-style names.
- Types and interfaces: `PascalCase`.
- CSS classes: follow the existing styling system and use readable, consistent kebab-case for custom classes. Do not rename utility classes generated by the styling framework.

## Supabase and SQL

- Tables, columns, indexes, triggers, and SQL functions/RPCs: `snake_case`.
- Keep existing database names stable unless a migration updates every dependent reference and includes a safe rollout/rollback plan.
- Migration filenames should use the existing timestamped prefix plus a concise snake_case action/subject, such as `20261011104727_secure_exact_referral_code_validation.sql`.
- Treat wallet, deposit, withdrawal, referral, allocation, reserve, and reward names as financial contracts: no bulk renames without a dependency audit and data-safe migration.

## Files and exceptions

- Application-owned React component files use PascalCase.
- Existing shadcn/ui files under `src/components/ui/` use lowercase kebab-case; keep that generator convention rather than renaming them.
- Existing TanStack-generated route files (including `src/routeTree.gen.ts`) are generated artifacts; do not hand-rename them.
- Existing route filenames, API endpoints, environment variable names, and external integration fields are compatibility-sensitive and should not be renamed solely for style.
- Environment variables use `UPPER_SNAKE_CASE` (for example, `SUPABASE_URL`).

## Safe cleanup workflow

1. Audit names and references first.
2. Separate style-only inconsistencies from public contracts and generated files.
3. Rename a symbol only when all imports/call sites can be updated together.
4. For database/API changes, add an explicit compatibility migration and update callers before removing old names.
5. Run ESLint, production build, and focused tests after each change.

## Initial repository audit

The repository already has a clear majority pattern:
- Application components such as `AdminEmailComposer.tsx`, `SupportTicketPanel.tsx`, and `TransactionRow.tsx` use PascalCase.
- Core service/library modules such as `admin-service.ts`, `deposit-service.ts`, `transaction-service.ts`, and `input-validation.ts` use kebab-case.
- The `src/components/ui/` directory uses lowercase kebab-case, consistent with generated shadcn/ui components.
- Supabase migrations use timestamped filenames with snake_case descriptions.
- SQL-facing identifiers such as `admin_profit_summary()` and `created_at` use snake_case.

These are intentional, layer-specific conventions rather than one casing rule for every file. New files should follow the convention for their directory and role. A broad rename of existing files or database objects is not warranted without stronger evidence of a concrete defect.
